# AC7 flight HUD and hangar HDR precision, 30 September 2026

Current status, 2 October: the user accepted native full-resolution UI and the corrected
wing/cloud/colour result, followed by the SR compatibility deployment. This document preserves
the SDR-display investigation and failed experiments. Native FP16 production and bounded GPU
colour correction address observed drift without proving DLSS's proprietary exposure cause.
See [the final aircraft/cloud corrections](ac7-plane-artifacts-20261002.md) and
[acceptance](sr-interop-performance-20261002.md#user-acceptance-and-release-replacement).

The user reported low-resolution flight UI, briefly sharp after unpausing, and patchy colour
bands during hangar departure. Six F9 sessions from process 170536 completed with three paired
samples each. The first three show hangar departure; the last three show flight and clouds.
These are SDR display runs. The user's device has no HDR display support and AC7 does not
provide native HDR display output. Here, HDR input means the floating-point scene buffer before
the game's tonemapper, whose values include luminances above 1. It does not imply HDR presentation.
The executable fingerprint remains the one in `ac7-motion-vectors.md`.
[Sanitized evidence](evidence/ac7-ui-hdr-20260930.json) records counts and fingerprints.

## Flight HUD producer

The flight draw trace supplies a producer the earlier briefing research did not cover.
PS CRC32C `b2f7719d`, SHA-256
`9faca5d9e57d6911f0077ad2959b2f172b6e5ec4fb263e8267eecf561d4274e3`,
1104 bytes, samples widget slot 1 at 1920x1080 and layer slot 0 at 800x452. It blends those
using alpha and rectangle tests, then writes an 800x452 RGBA8 target. This is a fullscreen
triangle, not the six-index widget quad the classifier recognized. The final composite
samples its unpromoted output. This establishes a low-resolution rasterization stage before
presentation; it does not yet establish the exact pause/resume timing.

The correction recognizes the producer at shader creation using size, DXBC container checksum
and CRC32C. It includes that shader in the draw prefilter and refreshes its output as a UI
promotion target on each qualifying draw, requiring the known widget input. It does not divert
the fullscreen blend into a transparent layer. Registry refresh follows actual production,
including cached widget contents. Pointer reuse at creation removes the old identity.
Matching against the captured bytecode passed; changing an instruction byte was refused.

The flight trace also has unpromoted scene post-processing intermediates. The existing chain
confirmation expects a producer to read the final composite, which does not describe every
flight pass. Those intermediates require a separate producer-chain correction; the HUD change
does not claim to repair all post-processing resolution or gate placement.

## HDR precision experiment

Raw R11G11B10 scene input retains smooth dark shading. Raw FP16 DLSS output has broad colour
steps, especially beside the bright doorway in capture 3. This is present in floating-point
data, not merely the TGA preview. The input maximum is 480; output reaches 482.75.

`tools/exposure-probe.cpp` runs a frozen 800x452 FP16 conversion of that input for 60 evaluations
into 1600x900 on RTX 4070 Laptop GPU, driver 616.92, Streamline 2.14.1 and DLSS 310.9.1.
Each condition uses a separate process, identity camera matrices, flat depth, zero motion/jitter
and a first-evaluation reset. These simplifications isolate colour precision; they do not replay
the game's temporal history. This hardware experiment is explicit and outside routine CTest.

| Condition | Result |
| --- | --- |
| Performance default, auto exposure | Reproduces patchy bands |
| Performance default, external exposure 100 | Byte-identical to auto exposure |
| Input clipped to 1, Performance default | Smooth dark shading, destroyed highlights; diagnostic only |
| Quality default, original full-range input | Smooth dark shading |
| Performance preset K, original full-range input | Byte-identical to Quality default result |

Selecting K was tested and briefly deployed as a compatibility workaround. The user correctly
rejected it as a solution because driver overrides can select another preset. The forced K
selection has been removed. It remains a diagnostic comparison, not a completed HDR fix.
Internal exposure/precision behaviour remains unproven; no processing-time comparison or
controlled native/bilinear baseline was captured.

The standalone probe subsequently intercepted NGX creation/evaluation using optional SDK headers
outside Git. The actual creation flags are `0x4b` with automatic exposure and `0x0b` with an
external exposure texture: HDR and inverted depth are preserved in both. This directly rules out
the lost-HDR creation flag for this repro. The external-exposure output remains identical.
Changing NGX pre-exposure to 100 with unchanged input also yields identical output. Multiplying
input by 100, passing pre-exposure 100 and dividing output by 100 changes the steps but does not
eliminate posterization. Neither an arbitrary scale nor highlight clipping is accepted as a
production correction. The proper preset-independent fix remains open.

## Input and output format comparison

The user suggested that the packed game format might be valid but suboptimal. The frozen-input
probe now accepts R11G11B10_FLOAT, RGBA16_FLOAT and RGBA32_FLOAT inputs, plus FP16 or FP32
outputs. The same decoded scene values were used for each input; R11 values fit exactly in FP16,
and widening them to FP32 adds no source detail. NGX parameter tracing queries each actual
resource descriptor immediately before evaluation, confirming the intended format and dimensions.

| Input | Output | Result |
| --- | --- | --- |
| R11G11B10_FLOAT | RGBA16_FLOAT | RGB identical to FP16 baseline; bands remain |
| RGBA16_FLOAT | RGBA16_FLOAT | Baseline |
| RGBA32_FLOAT | RGBA16_FLOAT | RGB identical to baseline; bands remain |
| RGBA32_FLOAT | RGBA32_FLOAT | Additional numeric precision; same broad bands |

These are separate 60-evaluation GPU runs at unchanged resolutions, with HDR and auto exposure
enabled. There are no nonfinite RGB outputs. The large precision loss therefore happens before
the final output-storage rounding, and changing input packing alone does not correct it. This
does not rule out another integration error or establish an internal proprietary-model defect.
Evidence includes output hashes and numerical differences. Native scene format remains unchanged.

## SDR colour-domain experiment and next capture

A diagnostic GPU run maps the frozen scene with `pow(x / (x + 0.18), 1 / 2.2)`, then supplies
that bounded perceptual image to NGX with HDR input disabled (`0x4a` creation flags). The
Performance default reconstructs it without the broad bands. This is an experimental tone curve,
not AC7's grading or a production fix. Its purpose is to distinguish the pre-tonemap colour
domain from the display-referred input domain. It does not justify disabling the HDR flag on
the existing linear input, clipping bright scene values, or applying a second tonemapper in game.

A possible supported route is reconstruction after AC7's own tonemapper and before HUD
composition. It needs verification of jitter/history, existing TAA, motion-blur/distortion order,
colour encoding, and the earlier promotion gates. Those are implementation requirements, not
properties established by this frozen image. No runtime colour-domain change is deployed.

F9 now additionally saves bounded raw snapshots after the captured tonemap (`6bcbd787` and
`5fb31417`), scene-effect (`a5c9147b`), HUD (`b2f7719d`) and composite (`2136e125` and `a7441be5`)
pixel shaders. These CRC32C identifiers only select diagnostics. There are at most 24 stage
readbacks per session; draw JSON records each file and result at the exact producer draw. VS
resource bindings are recorded as well, because stock tonemapping can read eye adaptation there.
Capture once with DLSS disabled through the running overlay, then enabled in the same scene, to
obtain the actual game's SDR intermediate rather than use the diagnostic tone curve.

## Online source check and corrected interpretation

NVIDIA's [31 March programming guide](https://raw.githubusercontent.com/NVIDIA/DLSS/main/doc/DLSS_Programming_Guide_Release.pdf),
sections 3.9 and 3.12, limits external exposure support to J/K and describes the newer presets'
exposure path. Consequently the unchanged external-exposure experiment does not rule out
internal auto exposure. The initial interpretation was too strong and is corrected here.
The guide also describes banding from incorrect HDR/exposure handling.

A [NVIDIA-confirmed UE plugin issue](https://forums.developer.nvidia.com/t/dlss-for-5-8-has-lots-of-ghosting/375449?page=2)
overwrote feature flags while setting inverted depth, losing HDR. AC7 uses our Streamline
integration rather than that UE5 plugin. The
[2.14.1 Streamline implementation](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.1/source/plugins/sl.dlss/dlssEntry.cpp)
combines HDR and inverted-depth flags with OR and forwards exposure/pre-exposure. Our wrapper
requests HDR. This source review does not inspect the effective proprietary-model internals.
No exact NVIDIA-confirmed report matching this AC7 frozen-frame failure was found.

## Capture and validation

The later on/off capture changes the interpretation of the whole image. The allocation selected
as tonemap output is GBuffer A earlier in the frame; our ungated promotion substitutes its reads
in lighting and reflection composition before that allocation becomes a post-process target.
The supplied DLSS input is therefore already damaged. The frozen-input experiments above remain
valid comparisons, but cannot attribute the missing lighting/reflections to DLSS exposure or
establish that all game inputs were correct. See the [ownership audit](ac7-renderer-roots-20260930.md)
for the exact requested/live resource evidence and tested phase correction. Reassess remaining
banding after this fix. The user now confirms lighting and reflections restored, while reporting
returned jitter/shimmer. The diagnostic SDR curve is not evidence that moving SR after tonemap
is the required solution.

The earlier final-screen dump failed because the preview decoder did not support the actual
R10G10B10A2 back buffer. Raw and preview paths now support it; route dumps preserve raw bytes
as well as a viewable preview. RGBA8/BGRA8 post-processing targets are also supported.
The WARP fixture checks exact ten-bit channels and the final-image preview.

The Windows MSVC Release verification gate for the phase fix and native root capture passes:
31 passed, five vendor-environment tests skipped, Rust formatting and lint passed. The colour
precision comparison is device-tested. Lighting/reflections are user-confirmed in AC7; HUD
transition behavior, remaining banding and temporal stability remain unresolved. F9 also records native
post-process scopes and converter fields to connect the next images to their engine producers.

The six motion sessions contain accepted primitives, missing history and size rejection. Native
decisions remain unchanged. These records alone do not assign a rejected component to a missile
or vehicle; transform-to-draw matching and cloud depth/history ownership are still open.

## Producer precision and bounded colour correction, 2 October 2026

DLSS Performance/Ultra exposure is explicitly a priority-one blocker alongside aircraft and cloud
defects. Changing NGX ExposureScale to5 in the frozen HDR repro is byte-identical to1 and is rejected.
The earlier format comparison used the same already-quantized R11 values. It ruled out a copy-format
fix, not higher precision during native lighting. GetSceneColorFormat is now hooked at the native
allocation/shader-parameter owner to select PF_FloatRGBA before scene writes. Actual new producer
values and visual effect require the user-run game capture.

A first-party GPU correction now compares DLSS output with the source-grid linear RGB and applies
three interpolated residual updates before the native graph consumes reconstruction. Source and
existing-output bounds prevent added highlight overshoot and dark ringing; captured depth protects
silhouettes. The game retains its own tone mapping, grading, bloom and exposure update. Every DLSS
mode uses the same pass, so no forced preset is involved. This is an observed colour-drift correction,
not proof of why the proprietary auto-exposure path produces the steps.

The frozen Performance repro visibly loses its broad bands, retains the original0.000192..482.75
range and exact alpha, and reduces source projection RMSE from3.02905 to1.17734. This metric is
not native-image MSE. The flight Ultra repro uses actual533x300 colour and depth, retaining its
outer silhouette and original peak after guarding. Both outputs are finite. Initial unbounded
residual/ratio versions and colour-only boundary rejection were discarded after ringing, overshoot
or remaining banding. Timings, image interpretation and replay limits are recorded in the
[artifact research](ac7-plane-artifacts-20261002.md). Moving-frame game acceptance remains open.
