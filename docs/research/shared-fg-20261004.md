## Colour and temporal inputs

SR reconstructs the pre-tonemap scene. The game completes its effects and tonemapping;
generation consumes that completed display-size backbuffer, containing the upscaled result.
The depth and normalized previous-minus-current pixel motion belong to the same source
frame and view. Generation does not run a second upscaler. SDK selection is independent of
SR selection, including DLSS SR with FSR or XeSS FG.

This first shared path declares no separate UI guide, matching the existing AC7 DLSS path.
The backbuffer contains HUD and overlay pixels. HUD-less colour and separate UI composition
remain a quality limitation to test in both games; these captures do not prove UI quality.

## Implementation and lifetime

The existing presentation bridge selects one cold-start provider. D3D11 games retain their
facade plus ordered shared upload; native D3D12 games use their engine's device, queue and
buffers directly. Unsupported provider creation forwards to the original chain. Provider
changes require restart, avoiding simultaneous vendor presentation owners.

`rsf_fg12_install`, CPU events, capture, submission confirmation and window association
are reusable runtime calls. Unity's shim installs interception before its Mono wait. Its
managed adapter inserts callbacks before EarlyUpdate and after PreLateUpdate without
replacing engine delegates. This brackets input/simulation, not individual device polls.
The plugin confirms capture only after Unity returns an actual submission fence identity.

AC7 captures dense depth/motion independently of the SR provider. D3D12 copies normalized
depth/motion into six immutable slots, retaining source session/frame/view identity. A wrong
view, unsubmitted capture, reset or missing CPU boundary disables interpolation. Command and
provider retirement protect slot reuse. FSR gets explicit shader-read states; source state
is restored afterward. Resize recreates FSR's fixed-size generation context after retirement.

Repeated identical options no longer disable FSR or reset FSR/XeSS temporal history. XeSS
limit-only changes preserve history. FSR reports callback activity without inventing a
confirmed presented-frame counter. XeSS uses its SDK present count. Released physical-chain
references precede provider destruction; the opposite order failed the first FSR fixture.
